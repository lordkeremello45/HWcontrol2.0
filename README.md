# HWcontrol2.0

**HWcontrol2.0 is a cross-platform PC hardware monitoring and control application** for Windows 10/11, Linux, and macOS 14+ Apple Silicon. It is designed to report CPU/GPU temperatures, memory and storage telemetry, fan speeds and other sensors when the operating system and hardware expose them; supported devices can also use safety-gated fan and performance controls.

It is a desktop PC utility—not an industrial automation/SCADA product, a serial hardware-flow-control protocol, or a DAW/mixer controller. Its verified runtime path is Flutter/Dart desktop GUI → authenticated localhost Go bridge → Go telemetry collectors and platform-specific control adapters. The C++/CMake AI and audio components run as separate native helpers; they are not the current hardware-control engine. **Hardware support varies by device, driver, operating system, and available permissions; this project is in Beta.**

HWcontrol2.0 is an open-source, cross-platform hardware monitoring, control, health and diagnostics platform built around a Flutter/Dart dashboard and an authenticated localhost Go bridge. Hardware collection and validated control adapters currently live in the Go bridge; C++/CMake AI and audio helpers are separate components.

> **Documentation:** The [current implementation status](docs/CURRENT-IMPLEMENTATION-STATUS.md) is the concise source for implemented, partial, unavailable and unverified capabilities. The wiki and platform guides provide detailed procedures.

> **Current channel: Beta.** Hardware support and control capabilities depend on the operating system, drivers, and detected hardware. Unsupported control paths remain monitor-only.

## What it does

- CPU, memory, SSD/HDD/NVMe, GPU and fan telemetry where exposed by the OS/driver
- Per-volume storage usage, free capacity and read/write throughput; device health is reported only when a trusted platform-specific health source is available
- Temperature history and configurable temperature alerts
- Hardware-control commands for supported platforms/devices
- Performance / Balanced / Quiet application presets; separate Windows 11 and Linux OS power-profile adapters with runtime validation pending
- Game Mode
- Safety-normalized Smart Fan Curve editor with a nonzero cooling floor, thermal emergency override and capability-gated automatic control
- Per-channel fan inventory, independent manual targets, local fan profiles, and CPU/GPU/hottest-sensor selection where the platform exposes validated PWM channels
- Optional read-only liquid-cooling telemetry through an externally installed `liquidctl` CLI (coolant temperature, pump/fan RPM, flow and level only when explicitly reported)
- Local temperature automation rules
- Bounded CPU-only microbenchmark
- Read-only battery capacity and charge-state panel (hardware validation pending)
- Healthy Core CPU/GPU thermal-condition indicator; not a silicon-wear or remaining-life estimate
- Optional local Gemma analysis; advisory only and not required for core monitoring
- Optional offline Piper text-to-speech integration (runtime/model supplied separately)
- Audio Controller Studio and offline aim-practice screen (not game-integrated)
- Local extension metadata/capability contract
- Local user profiles and fan-curve configuration
- Secure loopback communication between the dashboard and bridge
- Bridge diagnostics, hardware capability matrix, anomaly detection and fail-safe health states
- Persistent telemetry history and local profile storage
- Optional local AI support; the core application does not depend on the model being installed
- Verified GitHub Release update download with SHA-256 validation when release asset digests are available
- Cross-platform build, package, checksum and provenance validation in GitHub Actions

## Installation

### Windows

Use the guided Setup EXE installer for normal users. The MSI remains available for managed deployment, and ZIP/7Z are portable archive formats. The beta release may also include an unsigned MSIX preview; it is not signed with a trusted production publisher identity. A separate CI validation workflow installs MSIX using a temporary test certificate, which does not establish production publisher trust.

### macOS

Use the Apple Silicon PKG or DMG from the macOS Beta release. The `app-bundle.zip` asset contains the `HWControl.app` bundle and its companion runtime files.

### Linux

Use the DEB on Debian/Ubuntu-family systems, or the portable TAR/ZIP archive when appropriate.

#### Debian/Ubuntu APT repository (amd64)

HWcontrol2.0 can publish a signed APT repository through GitHub Pages after a stable Linux DEB release is available and the dedicated `APT_GPG_PRIVATE_KEY` secret passes fingerprint validation. The repository setup script pins the archive signing-key fingerprint and refuses to install a key that does not match it. Treat APT as available only after the Pages deployment has completed successfully and the repository endpoint serves its signed `InRelease` file.

Download and inspect the setup script, then register the repository:

```bash
curl --fail --location --proto '=https' --tlsv1.2 \
  https://raw.githubusercontent.com/lordkeremello45/HWcontrol2.0/main/scripts/setup-apt-repository.sh \
  --output setup-hwcontrol-apt.sh
less setup-hwcontrol-apt.sh
sudo bash setup-hwcontrol-apt.sh
```

After the script finishes successfully, install or update HWcontrol with:

```bash
sudo apt install hwcontrol
```

The setup script installs the repository key into `/usr/share/keyrings/`, writes `/etc/apt/sources.list.d/hwcontrol.sources`, and runs `apt-get update`. It supports Debian/Ubuntu-family amd64 systems only. The APT repository currently selects **stable** GitHub Releases; Beta-only builds are not automatically published to this channel. Repository registration does not guarantee that a package is available: if no stable Linux DEB release is published, installation will fail until one is available.

For detailed platform instructions, see the [Wiki](https://github.com/lordkeremello45/HWcontrol2.0/wiki). For a careful first install, checksum guidance and issue-reporting checklist, use the [Beta Quickstart](docs/USER-QUICKSTART.md).

## Language and localization

HWcontrol2.0 provides a **System Default** language option. The Language Service reads the operating system's current locale and resolves it against the localization resources bundled with the application. Manually selected languages are stored in the user's local settings and take precedence over the system locale.

When **System Default** is selected, the application re-evaluates the operating-system locale on startup. If the exact locale is not bundled, HWcontrol2.0 uses the matching language resource when available; otherwise its existing English fallback remains in effect.

## Security and release integrity

The local bridge listens on loopback and authenticates commands with HMAC-SHA-256. Release workflows publish SHA-256 manifests and GitHub artifact attestations where configured.

Checksums and attestations provide integrity/provenance evidence; they are **not** substitutes for OS-trusted publisher signing. Windows Authenticode and Apple Developer ID/notarization are only claimed when the corresponding trusted credentials and verification steps are actually present.

See [SECURITY.md](SECURITY.md) and the [security documentation](https://github.com/lordkeremello45/HWcontrol2.0/wiki/Security-and-Signing).

## Ada/SPARK security core

HWcontrol2.0 includes an Ada package using **SPARK** (`security/spark-core/src/hwcontrol_security.ads`) for contract-based validation of safety-sensitive fan commands. The core defines sensor-temperature bounds and checks command authorization, telemetry validity, integrity state, and critical-temperature conditions before returning an allow/deny decision.

- SPARK source: [`security/spark-core/`](security/spark-core/)
- CI workflow: [SPARK security core](.github/workflows/spark-security-core.yml), configured to build, test, and run formal verification.
- Scope: this is a security-policy component; it does **not** by itself prove that every GUI/Go Bridge/native-engine command is routed through it at runtime.
- Verification status: consult the linked GitHub Actions runs for the current result. The presence of SPARK contracts or a workflow is not, on its own, evidence that formal proof passed or that end-to-end enforcement has been validated.

## Architecture

```text
Flutter / Dart desktop GUI
        ↓ HMAC-authenticated localhost IPC
Go Bridge — telemetry, hardware identity, capability checks and platform adapters
        ↓
Windows / Linux / macOS APIs, drivers and device interfaces
```

The Go bridge is the current hardware collection and supported-control boundary. C++/CMake components provide separate local AI, audio and early Game Core functionality; they are not the current shared hardware-control engine. Ada/SPARK and Rust provide selected security-policy and FFI support, but end-to-end SPARK enforcement across every production hardware command is not yet verified.

## NVIDIA GPU development

The Go bridge can use `nvidia-smi` for NVIDIA GPU telemetry when the installed driver exposes the requested fields. This is separate from GPU-accelerated inference.

The native `llama.cpp` build supports an **opt-in CUDA configuration** for local AI development. CUDA is disabled by default so ordinary cross-platform builds do not require the CUDA toolkit. On a supported NVIDIA development machine with a compatible CUDA toolkit installed:

```bash
cmake -S . -B build-cuda -DHWCONTROL_ENABLE_CUDA=ON
cmake --build build-cuda --config Release
```

This option has been added to the build configuration, but CUDA-enabled builds and runtime performance must still be validated on actual supported NVIDIA hardware before claiming release support. Standard release artifacts should not be assumed to use CUDA.
